# HOW CODERADAR WORKS
*The mechanism reference. Written 2026-08-28 from three full code reads (circuit side, validator side, CLI audit) + Rung-0 empirical runs — not inherited from prior docs. File:line citations are load-bearing; if a citation drifts, the code moved, not the doctrine. Current as of the F11/F12 fixes.*

---

## 1. What it is

CodeRadar answers THE ONE QUESTION — **"is X counterfeit — yes or no"** — deterministically, then repairs what it can. Counterfeit = code that performs the *appearance* of work: identity returns, loops that don't accumulate, mutation theater, guards that guard nothing, canned data dressed as computation. The detection philosophy (detection/base.py:49–60) is four invariants:

1. Inputs must influence outputs.
2. Computation must be captured.
3. Iteration must accumulate.
4. A function must return a value OR have side effects.

**Two product modes:** (a) audit a submitted codebase (CB) and replace counterfeit with genuine code; (b) **monitor a live build** — a dev building a new app under the radar, counterfeits detected and repaired *as they're written* (a connection going down is seen the frame it breaks). A CB of nothing but stubs is the outline of a build → the app boots into monitor mode (owner ruling, F11). Expected product either way: counterfeit-free code = code that lives up to the claim made by the model.

## 2. Design laws (why it's shaped this way)

- **ONE PLACE TO LOOK.** Nothing upstream of the ranker scores, filters, ranks, or truncates. Detection emits raw observations; if a yes/no is wrong there is exactly one home for the bug. The 243 severity labels, 7 ranking operations, and 53 suppression thresholds surgically removed from detection were cataloged in `_removed_rankings.py` (the migration ledger). Mined 2026-09-05 (late sitting): every Category-C threshold is a row of `RULES_HARDENING_2026-09-05.md` §S.5 (45 of the 53 were still live in detection — F-LEDGER-LIVE); the file is archived at `.archive/fragments/excised_20260905L_removed_rankings_ledger.py.txt`.
- **ELECTRICITY = frame-after-frame animation.** The way you make a circuit's electricity is the way you make the dash move: frame after frame, like animation. That is WHY every frame is a brand-new full scan — `ast_scanner.py` forces `rescan_triggered = True` unconditionally in `get_full_graph`, bypassing its own cache. A cached frame is a lie in the screenshot.
- **SCREENSHOT PRINCIPLE.** Proof by observation, not proof by proxy. Assertion suites, demos, runners, git, path hacks are all **proxies for not running the src code** — things code *says about itself*. The circuit is what the code *is doing right now*. Hence the name: you **run against** the real source.
- **VIRTUAL WHITELIST.** Nothing is ever removed or modified in a dev's CB. Detritus is whitelisted — the artifact lives OUTSIDE the target (`system_scripts/whitelist_<repoid>.json`, repo-id = `sha256(resolved path)[:12]`) — and every pipe stage consults it. Detection still runs on whitelisted functions; results are force-passed with a disclosure tag, never silently skipped, and the mirror discloses `whitelisted_files`.
- **COPY-FIRST.** A verified snapshot of the target lands in `~/CodeRadar_snapshots/<name>_<ts>/` before anything touches the CB (sorted file-list diff + count match, abort on mismatch). Destroying a submitted CB is the worst possible outcome.
- **LEAVE-NO-TRACE.** The gearbox keeps a write-manifest and at teardown MEASURES the residue (S4): every CodeRadar-owned file still in the target beyond the two kept state mirrors, plus any bytecode that appeared during the run — never a fixed "zero". The two state mirrors are the one exception (owner ruling 2026-09-28): they live under `<target>/.coderadar/<same/sub/path>/`, persist after the stop as the run's log and are reported as `MIRRORS KEPT` (`cr_stop`: `mirrors_kept`), never as residue; `.coderadar/` is never scanned. Post-Rung-0 the verifier bar is **byte-identity against the snapshot including pycache, the kept mirrors exempt** (RUN_AGAINST_RULES.md rule 8); under MCP, also apart from the client's own edits, which it names in `cr_stop(expected_changes=…)`.
- **ONE FIX per infraction.** Agents receive exactly one solution, not a menu (`cheatsheet_builder.py::to_agent_prompt`: "This is not a menu of options"). A repair is a genuine before→after or it doesn't ship.
- **CORROBORATION ≠ REDUNDANCY.** Same conclusion from different method families = corroboration; duplicate reports of one signal = fake importance. Implemented at the ranker: a fact detection already recorded becomes ONE evidence token with `attests_with=NAI-xxx+NAI-yyy` (the engine's literal token key), never a second vote.
- **ARCHIVE, NEVER DELETE.** And never stub our own engine — a fake `calibrator.py` would be planting the exact species we hunt.
- **STRUCK (plan item 9, 2026-09-05): §4.2/4.3 statistical outlier detection / `ToleranceCalibrator`.** No working example exists in any copy, and a tolerance scorer has no place beside binary verdicts. The health check reports it as STRUCK (step 9), the daemon carries `calibrator = None`, and the document no longer promises it.

## 4. Boot: launch → gearbox → four gated processes

`./launch.sh [/path/to/target [--tracer lsof] [--pmc] [--trackers io,mypy,crc,vulture]]` — **the opening sequence** (rebuilt 2026-09-29; setup page Lane B, owner 2026-09-30). The dash and its overlay come up FIRST, before any step that reads the target, and every step has its own light on the overlay, in run order.

**The setup page** (`system_scripts/launch_setup.py`): with no target argument, `launch.sh` serves one page on the dashboard port (`copy_ports.json` "dashboard", default 8080) in the foreground, before any daemon is stopped or any state is cleared — the first action is the path field (checked as it is typed), then Enter or Start; pmc, the trackers and an optional purpose are the other choices. Start writes `system_scripts/launch_choice.json` (`--emit-shell` turns it into TARGET PMC TRACKERS PURPOSE), the server frees the port and the launch runs; the tab turns into the dashboard. Cancel, Ctrl-C or closing the page → exit 4 → "closed without Start — nothing ran, nothing changed". A refusal between Start and the gearbox (pmc without sudo, a bad tracker, …) re-enters the page pre-filled with its reason (`--back-to-setup --setup-error`). Refused at the door, with or without the page: `--no-copy` (exit 2 — the snapshot is **always** taken, there is no copy option), `--tracer eslogger` (exit 2 — the tracer is lsof only; `--tracer` may be omitted), `--pmc` without passwordless sudo right now (exit 2), a tracker outside io,mypy,crc,vulture (exit 2; absent = none run), and any target that is CodeRadar's own tree or CONTAINS it — its parent folder, home, / (exit 1, "choose the repo's own folder"). The steps, as `launch.sh` runs them:
- **Launch choices** (target, pmc, trackers; tracer is fixed at lsof) — validated before anything is touched.
- **Step 1 pre-flight**: pkill stale daemons (all four); clear stale state (`circuit_state.json`, `NOAI_VALIDATION_STATE.json`, `BUILDER_STATE.json`, `runtime_coverage.json`, `running.json`, `running.lock`, `.noai_state.json`, `.monitor_state.json`); `rm -rf system_scripts/.cr_pycache/` — engine-owned regenerable bytecode cache *(slot 11)*; delete `poll_config.json` outright — slider prefs never persist, the dashboard re-creates it with defaults at boot *(slot 2)*; prune per-run gearbox logs older than the previous run *(slot 13)*; archive `whitelist_*` / `cb_writes_*` whose repo-id ≠ the current target → `.archive/` *(slot 14)*; abort if :8080 busy.
- **Gearbox started in the background**: `gearbox.py <target> --staged system_scripts/launch_progress.json`. It records the lights for the steps already done, brings the dashboard up (the overlay is on screen from here), then waits for launch.sh's steps below — `done`, `failed`, or `orphaned` (launch.sh gone without a word); anything but `done` fails the launch with no daemon started.
- **Step 0 COPY-FIRST**: snapshot + verify (abort on mismatch); refuses a snapshot dir inside the target.
- **Step 1b health check**: `health_check.py` Steps 1–21 (plus 12b, the artifact scanner, printed as its own `▶ Step` marker — 22 markers in the report); a failure aborts the launch; the report is archived in `.archive/health/` every launch. Its light carries a detail line ("N/N steps pass · M not measured — report: <file>", N = the `▶ Step` markers counted in the report, so 22 on a full pass); on a failure launch.sh sets `FAIL_WHY` to the first failing health step, the EXIT trap publishes it as the stage's and the run's detail, and the gearbox raises with that detail (S9, 2026-09-29) rather than a generic "launch steps failed". The whitelist light reads "N .py scanned · M whitelisted · K unreachable by import (all scanned)"; the target-env light carries `target_env.py`'s own summary line.
- **Step 2 whitelist (seam S1, pre-daemon)**: `DetritusCleaner(target).scan()` → `whitelist_<repoid>.json` with `entries[{path, reason}]`; an owner-authored `functions` key survives regeneration (owner entries always win). Since 2026-09-29 EVERY `.py` is scanned: a module no import reaches is recorded under `unreachable_by_import` as a fact, never whitelisted; the whitelist holds only non-`.py` artifacts, the artifact scanner's whole-file stubs (`stub:<kind>`) and bytecode rows.
- **Step 2b target env**: the target's private env (`target_env.py`, built or reused under `.archive/target_envs/<repo_id>/`). A failed build never blocks the scan: the light reads the recorded status — `built`/`reused` is green, a failed build is **degraded** with its reason (the readers fall back to the engine's interpreter, Q5).
- **Step 3**: launch.sh marks its steps `done` and waits on the gearbox, which starts the daemons.

**The progress file** (`system_scripts/launch_progress.json`): `{overall, order, stages{key: {status, label, detail, started, secs}}}`. Step statuses: `pending` → `running` → `pass` | `degraded` | `fail`; `overall`: `running` → `done` (launch.sh's steps finished) → `ready` | `failed`. launch.sh and the gearbox write it at the same time, so both go through `launch_progress.update` — read-modify-write under an exclusive flock on `launch_progress.json.lock`, a temp file unique to the writer, then an atomic rename; a write that fails is reported on stderr and never stops the launch. Readers need no lock. The 12 steps: launch choices, pre-flight, supervisor (gearbox), dashboard, snapshot, health check, whitelist scan, the repo's Python env, circuit daemon (graph + first pass), wiring check, counterfeit scan (validator), solutions (cheat sheets).

**Gearbox** spawns in strict gates — all four "up" definitions live in ONE function, `gate_states()`. Order since 2026-09-29: the dashboard is spawned FIRST (before launch.sh's target steps, so the overlay is up for the whole sequence); after launch.sh reports `done`, the circuit daemon and its gate; then the **wiring check** (every node `circuit_state.json` marks not connected fails the launch, named on its light); then the validator and the Builder are spawned together and only their GATES run in order. After the last gate the gearbox re-reads the progress file and writes `overall: ready` only if all 12 steps are `pass`/`degraded` — otherwise the launch fails naming the open steps:

| # | child | gate | source of truth | timeout |
|---|---|---|---|---|
| 1 | circuit_daemon | `circuit_ready` | `circuit_state.json:daemon_phase ∈ {READY, RUNNING}` | 120s |
| 2 | noai_validator | `noai_monitoring` | `NOAI_VALIDATION_STATE.json:phase == MONITORING` | 120 + 2.0×n_py, cap 900s |
| 3 | cheatsheets (item 1, 2026-09-08) | `builder_monitoring` | `BUILDER_STATE.json:phase == MONITORING` — gate starts only after #2 passed | 60 + 2.0×failed rows, cap 900s |
| 4 | dashboard | `dashboard_up` | HTTP 200 on `127.0.0.1:8080` | 30s |

Gate polling is 0.5s with fail-fast if the gated child dies. Supervision: 1s tick, **no restarts** (owner 2026-09-29, S4: a crashed daemon's results cannot be trusted) — a child that dies, or is confirmed hung (process state T/Z, a stalled `circuit_state.json`, a failing dash HTTP gate, or a Builder heartbeat older than `HUNG_STATE_S` = 90s), stops the run — so does a child that dies during its own startup gate (P1: "<exit how> during its startup gate"; a gate that merely times out is still a plain startup failure) — the failure (daemon, exit code/signal or hang reason, last log lines) goes to the run feed, the progress file, the terminal and a red **failure panel** on the dash; the tester report / verdict read `run_trusted: false` with a `daemon_failure` record; every daemon but the dash is torn down and the dash stays up until Ctrl-C, exit 1. Manifest scan every 30s, staleness warning if `circuit_state.json` mtime > 30s. **Teardown** (`finally`; SIGINT, SIGTERM and SIGHUP — closing the terminal — all take it; P1: `log()` never raises — a dead terminal switches stdout to /dev/null — and `terminate_children` sits in its own inner `finally`, so no earlier teardown error can leave the daemons running): final manifest scan → SIGTERM all (each child's whole process group — B8), grace, SIGKILL escalation → the two state mirrors KEPT under `<target>/.coderadar/` (`MIRRORS KEPT: n …`, owner ruling 2026-09-28) → residue MEASURED (manifest ∪ fresh walk, the kept mirrors exempt: `RESIDUE CHECK: …`) and the bytecode verdict → manifest persisted with `teardown_verified`. Pre-flight keeps a prior run's mirrors too (`pre-flight: n state mirror(s) from a prior run kept in target`) — this run's daemons overwrite each one as its directory comes into view. Empirical (Rung 0): full boot 7s on a 42-file target; all-zero-live target now boots to monitor mode (F11 fix) instead of timing out the NOAI gate.

## 5. The circuit daemon — what one frame does

Startup: stale-session purge (repo-id mismatch clears old logs/state), whitelist load, initial AST scan, `INIT` write, CRC baseline load/create, initial mypy + I/O scans, `READY` write. Then the loop (~2.5s per frame, `poll_config.json:interval_ms`):

1. **Target hot-reload** — `poll_config.json:target_repo` re-read every cycle; change ⇒ purge + rebuild scanner.
2. **Depth hot-reload** — `max_depth` from poll_config (the dashboard slider is the authority — it writes this file, including `max_depth: 1` at dashboard boot).
3. **Whitelist hot-reload** — re-read from disk EVERY cycle, no caching.
4. **Full AST scan** — fresh re-walk (electricity principle). Discovery: `rglob("*")` (all files, not just .py), filtered by depth, whitelist (`scan_scope.is_whitelisted` — exact, dir prefix and glob — the same matcher the validator uses, P3), `__pycache__`, dot-prefixed segments, `.git`, `.egg-info`. **Connectivity rule** (ast_scanner.py:805–847): non-Python file ⇒ connected unconditionally; syntax failure ⇒ broken; otherwise broken iff a *local* import fails to resolve — third-party imports can never break a node, and **no import is ever executed**. String file-references (`open("x.json")`) become edges after the connectivity decision. Syntax check = subprocess `py_compile` with `PYTHONPYCACHEPREFIX` → engine-side `system_scripts/.cr_pycache/` (F12 fix — compiles only, never executes, zero target-side bytecode).
5. **Change tags** — per-line MD5-8 hashes, positional diff → compact ranges ("L12-L13, L45"); 3-slot FIFO per node, evictions to `daemon_log/change_tag_overflow.log`; tags persist across restarts; mtime-blind edits caught by content comparison.
6. **Process scan** — `ps -axww`, python processes matched to target scripts → `running.json` (flock-merged; entries from `entry_point_wrapper.py` preserved; dead PIDs pruned). System scripts excluded by substring — why target scripts must never share engine names (naming rule).
7. **Dataflows** — via `lsof` (the only tracer: `--tracer lsof` is the one accepted value and may be omitted; `eslogger` is removed from the MVP and refused at the door, owner 2026-09-30 — no root path, no fallback): two monitored PIDs touching one file/socket ⇒ evidenced `src → dst, channel, proof` edge.
8. **Runtime coverage** — which nodes are LOADED by running processes → `runtime_coverage.json`.
9. **Data type trackers** — every 8th cycle or on change: **CRC** function-level freeze check vs `mypy_n_contracts_watcher/baseline.json` (dashboard Accept rebuilds it); **mypy** whole-repo strict, clean-slate, whitelist as `--exclude` args; **I/O classifier** (own two-pass AST: sync/async, IO detection, `sync_exempt` by-design heuristics); **path hacks** every 10th cycle or on rescan.
10. **Write** — `circuit_state.json` atomically (mkstemp+rename) with ~18 top-level keys (nodes/edges/cycles/path_hacks/crc/mypy/io/dataflows/coverage/...), then the repo **mirror** `.monitor_state.json`, one per directory as it comes into view, under `<target>/.coderadar/<same/sub/path>/` (the root's at `.coderadar/.monitor_state.json`; location defined once in `system_scripts/scan_scope.py`): status `ALL CLEAR` ⇔ every `zero_signal` counter is zero — `['broken_imports','path_hacks','mypy_errors','sync_needs_review','dead_code_actionable']` — **and** `mypy_ran` is true (C5: a mypy scan that never ran — probe failure, rc≥2, timeout — cannot carry ALL CLEAR; `mypy_ran`/`mypy_rc` published beside the counts) (circuit_daemon.py:1113). Whitelisted infractions stripped from every section; `whitelisted_files` disclosed.

**Change detection (S1, 2026-09-29).** Each tick the scanner fills `changed_files` with every file new, content-changed or deleted THIS tick (the same detection that drives the mtime cadence); that list is what re-runs mypy/vulture, the CRC turn and the path-hack re-check, and a deleted/renamed file's caches, line hashes and change tags are dropped. Change tags persist atomically (temp + rename).

Per-cycle errors are caught with 1→60s exponential backoff. SIGTERM honored via flag + interruptible sleep.

## 6. The NOAI validator — the judging half

Waits for circuit READY, then `run_baseline()` (a follow-up baseline 20s later, then incremental mode):

**Stage 0–1: whitelist + detritus.** Whitelist artifact loaded (file entries + `functions` entries). DetritusCleaner runs scan-only; safety valve: if everything is detritus (no entry points), the live filter is discarded — but the whitelist union still applies (the persisted artifact is authoritative). Zero files after filtering ⇒ **monitor mode** (F11): `stage_output` writes an honest empty MONITORING state; never a parked phase.

**Stage 2: discovery.** `rglob("*.py")` minus `__init__/setup/conftest/__main__`, rca exclusions, and the detritus∪whitelist set.

**Stage 3: the validator** (`file_validation.validate_directory_async`). Per file: 2MB cap → `ast.parse` (SyntaxError becomes a real NAI-208 infraction) → per-function pipeline → whitelist consult #2 (function entries force-pass with `WHITELISTED` warning — detection ran in full). **The verdict** (`validator.py:185`) is three binary gates, first hit wins:
1. **STRICT checks** — 9 pure AST predicates (NAI-xxxS ids: 009S, 016S, 017S, 021S–026S; `strict_checks.py` STRICT_CHECKS) ⇒ immediate fail.
2. **Hard requirements** — function-type classification (FunctionIdentifier + canonicals) ⇒ boolean invariant checklist.
3. **AIFakeDetector** — ~190 checks across 10 mixin families; **any observation fails the function** ("the check itself IS the verdict"). An observation is a raw dict — `{tag, line, evidence-keys}` — **no severity, no message, no confidence anywhere** (base.py:97). Human strings are manufactured later by `_format_observation`.

**Module and class level (plan item 4, 2026-09-05).** `validate_module` emits FINDINGS (not warnings) for a module-scope `sys.path` / `os.environ` hack (NAI-094 — same predicate as the circuit's path-hack detector, module scope only) and for a hallucinated name in ANY module-scope `from X import Y` (NAI-210 — X resolved honouring the relative `level` via `_resolve_import_file`; a module that is not local or carries `import *` / `__getattr__` is NOT MEASURED, never guessed). `validate_classes` flags an empty class (NAI-213; exception / typing bases, decorators and metaclass keywords exempt). `_check_abstract_shells` runs after the per-file pass with every tree in hand and flags an ABC with abstract methods that no scanned class subclasses (NAI-214 — the message names the scope searched). Per function, `_check_canned_return` (NAI-212) fires on a body that is one `return` of literal nested rows, and NAI-079 now covers `open()` / `Path()` / file operations for absolute and `..` paths. Species → code cross-references live in `SPECIES_DICT.json`.

**Repairs — moved out (items 1–2, 2026-09-08).** The validator STOPS at infractions. Possible solutions, the Ranker's decision and the mirror are the Builder daemon's (§6a). The inline `stage_cheatsheet` was archived after item 2's parity proof (`.archive/runs/something_for_nothing/builder_parity.json`: BUILDER_GE_INLINE, 70 rows, 0 regression; the inline `rel::func` key collapsed same-named defs — the Builder keys by `file::function::line` and takes the def at the infraction's line) together with the reviewer's verdict classes and the schema: `.archive/archived_20260908/`.

**Cross-file RCA scope (plan item 6, 2026-09-05).** `RootCauseUnit(dirpath, files=py_files)` (and through it `CallerTracer(files=)` and `ImportTracer`), `ImportGraphBuilder(dirpath, files=py_files)` and the already-fed `CallerMapBuilder` all index exactly the validator's whitelist-filtered list — no own `rglob`. RCA candidate files are clipped to that list (`rca_scope.candidates_clipped_outside_list`), so a live module importing a venv-internal package cannot drag the venv back in. `cross_file_analysis.rca_scope` states the scope; `tier2_status` states that `origin_tracer` and `onion_peeler` are runtime tools — NOT MEASURED on the static path, fed only by executed proof (item 8) — instead of the old empty lists.

**Edits-only cycle (plan item 7, 2026-09-05).** At discovery — before any stage reads a file — the daemon seeds `node_hashes` (relative_path → sha256 of the bytes on disk; S2 2026-09-29, never from the circuit after the baseline, so a file edited or added during the baseline is still caught by the next tick). Each poll, `check_incremental` compares the circuit's current hashes against that map: a changed hash on a scanned file → that whole file is re-ingested through `stage_ingest_incremental` (all functions + module level; an edit changes context for everything in the file); a NEW `.py` the whitelist does not exclude joins the scanned list as an edit (the whitelist test is `scan_scope.is_whitelisted` — the ONE matcher for exact path, directory prefix and glob, the same one discovery uses — S2); a scanned file whose node vanished and is gone from disk drops out. Unchanged trees cost nothing; there is no follow-up re-baseline and no re-walk. A tick that raises is logged with its traceback and the loop goes on with backoff; a first baseline that raises does not end the daemon (S2). Baseline `cross_file_analysis` is carried into the incremental mirror write, marked stale for the edited files.

**Executed proof (plan item 8, 2026-09-05).** `system_scripts/entry_point_wrapper.py` runs a target entry point the way `python script.py` would (sys.path, `__main__`), with `sys.dont_write_bytecode` and an import hook that records every TARGET file actually imported with its SHA256 at execution (`entry_point_info.json`, saved on every new import so the proof is visible while the script runs) and a `running.json` entry tagged as coming from the entry-point runner while the PID lives. ## 6a. The Builder — the fourth daemon (item 1, 2026-09-08)

`no_aivalidator/BUILDER_DAEMON.py`, gearbox child #4, `-m no_aivalidator.BUILDER_DAEMON`. It waits for the validator's MONITORING phase, then every 2.5 s: mtime changed → read the state under the shared lock → sha256 of the bytes; unchanged bytes → nothing. Target change → reset (its own files purged), phase WAITING. SIGTERM → stop, no final write. Phases `STARTING → WAITING → BUILDING → MONITORING`.

**One cycle.** Whole-set facts once: graph context from `circuit_state.json` (depth = longest importer chain, dependents = importers), one `ContextLinesCalculator.scan()` with one recommendation per flagged file, one parse per flagged file, `ProjectProfile` once per target. Infractions ordered roots-before-fruits by the plain tuple `(-depth, -dependents, line)` → `fix_order`. Evidence per row assembled flat (`rule_id=`, the three coupling scores, `depth=`, `dependents=`, cross-file tokens with `STALE:` when the validator says the file was rescanned, semantic tokens de-duplicated by span with `attests_with=`). Per row, under `asyncio.gather`: every deciding rule id is dispatched through `_rule_fixer_map` (NAI-071 / 092 / 093 today; item 4 grows it); each rewrite becomes a `SolutionCandidate` carrying **observations** — `parse=ok|fail:<msg>`, `differs=yes|no`, `safety=clean|<issue>` (from `CodeAnalyzer.analyze`), `quality=<note>`, later `tester=failed:<digest>` — then `SolutionRanker.decide(candidates, error_message, rca_evidence, target_code)` returns `Decision(pick, why, considered)`: a candidate observed `parse=fail`, `differs=no` or tester-failed is not pickable; none pickable → `pick=None`. **Tie-break** (S10b / I-80, owner 2026-09-29; `knowledge_base.py` `TIE_BREAK_STEPS`), applied only between exactly equal totals, AFTER the score: an applicable rewrite beats a suggestion; a real simplification beats a "not implemented" placeholder (I-80b: the placeholder reads weight 0 in every family, so it can no longer outrank a real rewrite on score either); then rule id — its place in the row's published rule ids (the validator's order, deciding rule first), then the id's text; then the smaller rewrite (fewer after-code characters); then the variant's name; the list index only as the very last fallback. A variant list's order is no longer policy — reversing one never changes the pick. **Shape-only variants** (`SHAPE_ONLY_VARIANTS`, today NAI-021S's `no_rewrite_shape`, I-78): a rewriter's named "no rewrite; emit this shape" entry is published as a prescribed shape (a suggestion), never gated, tested or applied. **Nothing overturns the pick afterwards** (FIX 11: the syntax re-check, the reviewer gate and the schema vetting are gone). A row is rebuilt only when its `row_hash` (the infraction's own fields) or its evidence changed; otherwise last cycle's row is reused with `fix_order` refreshed. While a cycle runs the Builder writes its heartbeat every `BUILD_BEAT_S` = 30s (a third of the gearbox's 90s hang limit, S4), so a long rebuild never reads as a hang; between cycles it beats on its FIX_46 cadence, so a Builder truly stuck between cycles still goes quiet and is caught.

## 10a. The MCP form — the agent seat (release form, owner 2026-09-16; source of truth: `coderadar_mcp/server.py` INSTRUCTIONS and `coderadar_mcp/README.md`)

The three P4 seats (vis-graph, replacement, tester) collapse into one client holding `cr_wiring`, `cr_apply`, `cr_run_module` + `cr_report_outcome`. No editor extension, no new agent.

**Path-first (R1).** The server starts with **no target**; the dev names the repo ("scan ~/code/myrepo" or the `/mcp__coderadar__scan <path>` prompt) and the seat calls `cr_watch(target=<path>)`. Until a target is bound every other tool except `cr_stop` answers `no target — call cr_watch with the repo path` (`cr_stop` always tears down whatever this CodeRadar runs). `~` expands; a relative path resolves against the server's working directory (the client's, where `claude` was started — not the dev's shell) and a refused one is echoed back as the absolute path it resolved to. `cr_watch` refuses, in one sentence each: a missing directory, a directory with zero `.py` files in the scan scope, CodeRadar's own tree, a second different target while one is live (`cr_stop first`; the same target again just attaches), this tree's launch setup page open on the dash port with no target chosen yet (choose there, or `cr_stop` closes it), and a busy dashboard/health port held by anything else (it names the holder). Tracer is `lsof` only; trackers are drawn from `io,mypy,crc,vulture` (default `io,mypy`).

**The launch.** `cr_watch` runs this tree's `launch.sh` with the same gates as `run_proof.sh up` (§4) and **blocks until every gate passes or its budget runs out** — the budget is derived from the gate timeouts (`session_tools._gate_budget` over `gearbox.py`'s own constants): 2190 s + 2 s per `.py` file, capped at 2970 s (36.5–49.5 min), published as `gate_budget_s`. A client whose tool timeout is shorter is cut off while the stack keeps coming up; then, or in a new seat, the seat does NOT ask `cr_status` (it answers "no target" until the seat is bound) — it calls `cr_attach(target=<the same path>)`, which answers MONITORING (attached) or names the launch still in flight and its phase. A live daemon of this tree is recognised by its process — an interpreter running one of the daemon files or modules (`gearbox.py`, `circuit_daemon.py`, `proof_dashboard.py`, `-m no_aivalidator.NOAI_VALIDATOR_DAEMON`, `-m no_aivalidator.BUILDER_DAEMON`, and the setup page's server `launch_setup.py --port …` — never its `--emit-shell` / `--submit-purpose` helpers, which live for milliseconds and hold no port) with cwd = this tree — never by a command line that merely contains a daemon's name (C3 (b), 2026-10-01). A setup page open before Start is therefore named as such (`the launch setup page is open on the dash port — no target chosen yet`), never as the previous launch's target, and `cr_stop` closes it — nothing ran (D2 / Q-H1-10).

**The 13 tools** (`tool_interface.py` is the gate: contract, source of record, input/output schema and the files each tool writes, per tool; `system_scripts/mcp_interface_proof.py` holds it). Session: `cr_watch`, `cr_attach`, `cr_stop`, `cr_hand_back`. Read (write nothing): `cr_status` (phase, gates, band, health, `finished`), `cr_infractions` (paged by file, 50 rows a page; `apply` is `yes` only for a row with a concrete diff rendered at the site, `review` for a template-only shape ranked after every `yes`, `no` = nothing to apply), `cr_row`, `cr_wiring` (edges `possible` / `live` / `severed`), `cr_data_types` (the trackers and `finished`'s `issues_scope`), `cr_intent`. Write: `cr_apply` (returns a MULTI-HUNK unified diff rendered against `replace_span_live` and writes nothing to the target — the client applies each `@@` hunk by its context lines in its own editor; one apply lease recorded beside the channel), `cr_run_module` (the target's script or runner through `entry_point_wrapper.py`: the entry-point proof, laid BEFORE any edit and AGAIN after the apply pass), `cr_report_outcome` (the ONE verdict write: one Item-5 line on the return channel, `confirmed` or `failed` — no other word parses; the Builder joins on digest AND `replace_span` and the Ranker re-decides).

**Writes, named.** CodeRadar never edits the repo's code. The only files it writes in the repo are the two state mirrors under `<target>/.coderadar/<same/sub/path>/` (§2 LEAVE-NO-TRACE) — kept after `cr_stop` as the run's log, reported as `mirrors_kept`; the seat leaves `.coderadar/` alone and never touches it as part of a repair. Everything else lives in CodeRadar's own tree: `cr_watch` / `cr_stop` / `cr_hand_back` write the run's log, snapshots, teardown md5 listings + diff and `tester_report.json` under `.archive/runs/<repo name>/`; `cr_apply` appends one apply-lease record and `cr_report_outcome` one return-channel line (plus one confirmed-ledger record on `confirmed`), both in `system_scripts/`; `cr_run_module`'s entry-point runner writes its running-state files there and puts back, from the launch snapshot, any file the RUN itself wrote inside the target (reported as `target_writes`). The launcher `coderadar-mcp.sh` exports `PYTHONDONTWRITEBYTECODE=1` and points `PYTHONPYCACHEPREFIX` / `MYPY_CACHE_DIR` at `system_scripts/.cr_pycache/mcp_<ts>/`, as `launch.sh` does for its own children (C3 (f), 2026-10-01).

**The end of a seat.** Before `cr_stop` the seat calls `cr_data_types()` and reports the mypy reading (import_errors, total_errors, files) and the io reading (functions, io_functions, exempt) to the dev even when they read 0 or "not measured", and quotes `cr_wiring` once (live-edge count; its `why` line when 0). Then `cr_stop()` — SIGTERM the launcher (its own handler runs the gearbox's leave-no-trace path), or, when no launcher owns the daemons, each daemon's whole process group (C3 (a)); it proves the target byte-identical to its launch snapshot apart from the kept mirrors and the client's own edits (`expected_changes`; anything else lands in `unexpected_changes`), reads `daemons_exited` and `residue_clean` from the gearbox's per-run log and names that file as `teardown_source` (null = NOT MEASURED, `error` says why), and repeats a one-line `trackers` backstop. `cr_hand_back()` comes LAST: the gearbox's teardown writes `tester_report.json` before its children stop, so a hand-back published while the daemons are live is overwritten (it says so in `error`); after `cr_stop` it reads `BUILDER_STATE` and the return channel, which outlive the daemons.

## 12. Glossary (owner vocabulary)

**CB** — a dev's codebase, submitted or under live build. **Counterfeit** — code performing the appearance of work. **Detritus** — everything in a CB that isn't live code (species catalog: SPECIES_DICT.json). **Virtual whitelist** — the detritus stripper that never touches the CB. **Circuit / electricity** — the live import-graph under frame-by-frame rescan; the animation IS the proof. **Overlay** — the startup overlay that lifts only when both daemons are truly ready. **The two mirrors** — a mirror of the current dashboard, auto-generated for each target-repo folder under `<target>/.coderadar/<same/sub/path>/` for the agent seat (MCP, §10a) and kept after the stop as the run's log: the **counterfeit-code mirror** (`.noai_state.json`: every counterfeit-code infraction with its best solution and location) and the **dash mirror** (`.monitor_state.json`: every non-counterfeit infraction, and — pinned P-1 — the vis graph). **Cheatsheets / the Ranker** — the repair package and its pipeline (the Reviewer included) and its single decision point; possible solutions → ONE best solution per infraction; neither "cheatsheet" nor "Builder" ever appears on the dash. **Proxy** — any stand-in for running the real source. **Run-against** — the act and the fixture: CodeRadar runs the real code against reality. **Monitor mode** — honest empty baseline over an outline CB, watching the build. **Like we were never there** — the teardown post-condition, verified.

## 13. The calibrator — how a family's disposition is decided (2026-09-06)

**What it is.** The rules MEASURE; the ranker DECIDES. Every emitted rule id has a row in `system_scripts/rule_dispositions.json` (257 rows: `disposition` = `deciding` | `context`, `class`, `evidence`). A row with a deciding id FAILS; a context id is published, dimmed, and never decides. The table is data — the ranker reads it (`VerdictRanker._load_dispositions`), nothing is inferred, and **gate step 18** (`system_scripts/disposition_check.py`) fails the launch on a missing row, a strict∩context row, a stale row, a deciding family without evidence (`disposition_close.json` mode `unevidenced_deciding = FAIL` since slice 2) or a lost plant of a frozen family (the recall guard re-runs every archived planted target in-process). The calibrator is the procedure that moves a family from deciding to context — and the only knobs it has are a family's disposition, an instrument-gap fix (a language / stdlib / scope FACT, `INSTRUMENT_GAPS.md`) and a body-shape refinement that is never a magnitude. The false-verdict rate on honest code is REPORTED, never targeted.
